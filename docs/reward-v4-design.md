# ShopSimulator 购物奖励函数设计方案

> 状态：已实现并启用；执行流程见 [Reward v4 完整重跑手册](reward-v4-workflow.md)。
> 奖励版本：shopsimulator-reward-v4。
> 适用流程：Baseline → SFT → GRPO → Evaluation。
> 核心输出：完整终局、确定性奖励、证据明细和可复现的判定原因。

## 1. 目标与适用范围

本方案奖励 Agent 在用户授权范围内，依据可验证信息完成商品搜索、详情浏览、规格选择和购买。评分关注购买正确性、明确偏好、错误决策损失和必要核验。

评价对象是最终订单：

$$
x=(\text{商品 ASIN},\ \text{最终规格组合},\ \text{最终规格价格})
$$

搜索页最低价、曾经选过的正确规格、商品页面上存在的某个选项，都不能替代最终订单事实。

保留 gold_purchase 作为严格成功标签。严格成功必须具有完整、合法的购买终局，满足本方案的 Gold 判定条件，且 reward_valid=true。Gold 的识别依据是终局事实和标签，不是奖励是否等于 1。

第一版面向单商品购买任务。数量、运费、优惠、库存、配送时效、店铺服务和售后成本等条件，只有在环境能真实表达、公开并可靠核验时才能纳入。缺少支持时，不假设默认值，也不构造模拟满意度。

只要求“推荐几款，我再决定”的任务不属于自动购买任务，不进入本轮购买训练集。训练数据始终与 data/evaluation/tasks.jsonl 隔离。

本文中的数值均为待验证的工程初值，不是通过真实用户研究估计出的满意度或货币损失。

## 2. 评分由谁负责


| 角色          | 职责                                         | 是否决定奖励         |
| ------------- | -------------------------------------------- | -------------------- |
| 数据构建器    | 把用户要求整理为结构化合同，校验可评分性     | 在运行前确定评分依据 |
| 人工审核者    | 处理歧义、核对抽取结果、审核规则与特殊严重度 | 审核并冻结规则       |
| 购物 Agent    | 选择搜索、浏览、规格选择、购买或停止动作     | 否                   |
| 环境验证器    | 比较最终订单与合同，核查轨迹证据             | 是，按固定规则执行   |
| Reward 计算器 | 根据验证结果、公式和参数输出分数             | 是，确定性计算       |

Agent 不提交“我满足了哪些要求”“请给我多少分”等评分输入。其自然语言声明不能代替工具状态和商品证据。

可选的离线语言模型可以帮助抽取需求，但只能生成候选结构，不直接生成最终奖励、任意严重度或新的满意度函数。最终结构必须经过字段校验、冲突检查和审核后冻结。相同合同、相同订单、相同有效证据，应得到完全相同的分数。

## 3. 从自然语言得到可执行的需求合同

### 3.1 处理流程

1. 读取用户指令和已有任务标注。
2. 抽取原文片段、商品字段、操作符、数值、单位、否定范围和替代关系。
3. 将必须条件和软偏好分开。
4. 将可评分要求映射到有限的比较器和满意度函数。
5. 规范化单位、别名和规格轴；去重语义相同的要求。
6. 检查矛盾、缺失参数、用户授权、商品数据和环境工具支持。
7. 审核后冻结合同，记录版本和哈希，再用于采集或训练。

不得根据某次 Agent 轨迹、购买结果或组内奖励，反向修改该任务的合同。

目标商品只用于校验标注、解析已有规格轴和确认任务可达性。目标 ASIN、隐藏的 Gold 规格和未写进用户指令的商品特征，不能成为新增购买要求。

### 3.2 必须条件与偏好的区别

必须条件决定“这笔订单是否允许购买”；偏好决定“在允许购买的订单中，用户更喜欢哪一种”。


| 原文                     | 必须条件             | 偏好                       |
| ------------------------ | -------------------- | -------------------------- |
| 买白色手机               | 颜色=白色            | 无                         |
| 必须256GB版本            | 容量=256GB           | 无                         |
| 至少256GB                | 容量≥256GB          | 无；不自动奖励更大容量     |
| 256GB起步，最好512GB     | 容量≥256GB          | 容量接近512GB，达到后饱和  |
| 白色或黑色都行           | 颜色属于{白色, 黑色} | 无，两个值等价             |
| 白色优先，黑色也可以     | 颜色属于{白色, 黑色} | 白色优于黑色               |
| 最好白色，颜色不限       | 无颜色限制           | 白色得高分，其他颜色仍允许 |
| 不要红色                 | 颜色不等于红色       | 无                         |
| 预算5000元以内           | 最终规格价格≤5000元 | 无                         |
| 预算5000元以内，尽量便宜 | 最终规格价格≤5000元 | 启用价格效用               |
| A型号缺货才允许B型号     | A不可购买时才允许B   | 条件替代，需要可靠缺货证据 |
| 好看、耐用、性价比高     | 暂不能直接确定       | 必须先解决语义与数据可测性 |

“白色优先”未说明其他颜色是否允许时，不自动等同于“只能白色或黑色”。对改变购买范围的歧义，必须在数据构建阶段解决；无法解决的任务不进入主训练集。

“至少256GB”的比较规则接受512GB，不代表用户表达了更偏爱512GB。允许集合与偏好排序是两件独立的事。 

### 3.3 有限的条件类型


| 类型       | 比较器                      | 例子                       |
| ---------- | --------------------------- | -------------------------- |
| 标准化枚举 | eq、neq、in、not_in         | 颜色、品牌、型号           |
| 数值       | eq、ge、gt、le、lt、between | 容量、重量、尺寸、价格     |
| 布尔功能   | true、false                 | 是否支持指定功能           |
| 类目       | 冻结的类目映射与层级规则    | 手机，而非手机壳           |
| 条件授权   | if + 已支持的基础条件       | 有可靠证据时允许指定替代   |
| 组合要求   | all_of、any_of              | 同时支持两个功能，或二选一 |

别名匹配、单位换算和数值边界在比较器中固定。例如 2L 与 2000mL 可视为等价；型号 A20 与 A200 不等价；“不支持防水”不能命中“支持防水”。

商品字段未出现不等于确定违反。明确匹配返回 pass，明确冲突返回 fail，事实不足返回 unknown。

### 3.4 多种说法如何统一

不为每一句自然语言编写单独奖励函数，而是把多种表述映射到有限语义结构：

- “优先白色”“首选白色”“最好白色”：首选值候选，需确认是否有限定的允许集合。
- “不超过”“最多”“以内”：上界候选，需核对是否包含边界。
- “至少”“起步”：下界候选。
- “只要”“就买这个版本”：精确值候选。
- “A不行再B”：条件替代候选，不能简化成 A、B 无条件都允许。
- “预算左右”“大概”“差不多”：近似要求，需要已审核的容差或进一步澄清，不能默认加减10%。

可以使用规则与词典覆盖常见表达，并通过离线模型补充复杂抽取。运行时只能使用已审核的函数注册表，不执行模型生成的表达式或代码。

### 3.5 无法量化的要求

“漂亮”“高端”“耐用”“性价比高”等词，不能直接转换成任意0到1分。

处理规则：

1. 若原文同时给出客观解释，使用该解释，例如“耐用，要求金属外壳且支持三年保修”；仍需数据可核验。
2. 若任务作者补充客观定义，该定义必须写回 Agent 可见指令，不能只存在于私有评分规则。
3. 若无法可靠定义或环境不支持，任务标记 needs_review 或 unsupported，排除出本轮主训练集。

“未提出偏好”和“提出了但解析不了”不能混为一谈。后者不得静默删除后按满分处理。

## 4. 偏好满意度函数

### 4.1 适用原则

只有用户允许妥协的要求才能进入偏好评分。允许集合的边界属于必须条件，首选排序属于偏好。

每个偏好 j 使用注册函数计算：

$$
s_j(x)\in[0,1]
$$

0 表示该偏好没有获得满意度奖励，不必然表示订单禁止购买；是否允许购买由必须条件单独决定。

价格优化单独进入价格效用，不再重复进入偏好总分。同一个语义要求只登记一次，重复提及不能增加分数。

### 4.2 首选值加可接受替代

函数名：categorical_preferred_v1。

- 首选值：1.0。
- 用户允许的非首选值：0.5。
- 超出允许集合：必须条件失败，进入错误购买分支。
- 若用户明确“不限制此字段”，所有合法值均属于允许范围。

例：“白色优先，黑色也可以”。


| 最终颜色 | 允许购买 |           满意度 |
| -------- | -------- | ---------------: |
| 白色     | 是       |              1.0 |
| 黑色     | 是       |              0.5 |
| 红色     | 否       | 不参与购买正奖励 |

0.5 是固定的工程编码，并不代表测得用户只满意50%。

### 4.3 明确的多级排序

函数名：ordered_choices_v1。

用户明确给出 K 个有顺序的等级，r为最终值所在等级，从0开始：

$$
s(v)=
\begin{cases}
1,&K=1\\
1-0.5\frac{r}{K-1},&K>1
\end{cases}
$$

例：“白色最好，银色其次，黑色也可以”。


| 值   | 等级r | 满意度 |
| ---- | ----: | -----: |
| 白色 |     0 |   1.00 |
| 银色 |     1 |   0.75 |
| 黑色 |     2 |   0.50 |

同一等级可以包含多个等价值。没有顺序的“A或B都行”只产生集合必须条件，不额外奖励A或B。

### 4.4 有最低值和期望值的数值偏好

函数名：numeric_increasing_saturated_v1。

用户给出最低可接受值 L 和期望值 T，且 T>L：

$$
s(v)=\operatorname{clip}\left(\frac{v-L}{T-L},0,1\right)
$$

例：“至少256GB，最好512GB”。


| 容量  | 允许购买 |           满意度 |
| ----- | -------- | ---------------: |
| 128GB | 否       | 不参与购买正奖励 |
| 256GB | 是       |              0.0 |
| 512GB | 是       |              1.0 |
| 1TB   | 是       |              1.0 |

到达期望值后饱和，避免无限奖励用户未要求的高配置。只有“至少256GB”时，不启用此函数。

### 4.5 有目标值和上限的数值偏好

函数名：numeric_decreasing_saturated_v1。

用户给出理想上限 T 和可接受上限 U，且 U>T：

$$
s(v)=\operatorname{clip}\left(\frac{U-v}{U-T},0,1\right)
$$

例：“最好200g以内，220g也可以”。

- 200g及以下：1.0。
- 210g：0.5。
- 220g：0.0，仍允许购买。
- 超过220g：必须条件失败。

若 T=U，只产生必须上限，不计算分母为零的函数。

### 4.6 功能偏好

函数名：boolean_preference_v1。

例如“有无线充电更好，没有也能接受”：

- 已证实支持：1.0。
- 已证实不支持：0.0。
- 事实未知或没有有效偏好证据：按保守规则取0.0，并记录 unknown，不伪装成已证实不支持。

如果用户要求“必须支持无线充电”，则它属于必须条件，不使用这个偏好函数。

### 4.7 条件替代

例：“只有A缺货才买B”。

必须先确认条件分支是否触发：

- 环境证据确认A不可购买：启用允许B的分支。
- A可购买：不能擅自购买B。
- 搜索没有找到A：不能推出A缺货。
- 环境没有可靠库存或可购买性证据：此任务不进入第一版主训练集。

不能为解决解析困难，把条件替代降级成无条件替代。

### 4.8 多个偏好如何聚合

第一版采用保守的最小满意度：

$$
S_{\mathrm{pref}}=\min_{j\in P}s_j
$$

没有非价格偏好时，定义 S_pref=1。

例如，颜色满意度1.0、重量满意度0.5，则 S_pref=0.5。这样的奖励表示：订单的偏好质量受最不满意的一项限制。

此规则不需要推断“颜色究竟比重量重要几倍”。其限制是：最差偏好不变时，改善其他偏好可能不改变总分。因此所有单项分数都应保留，便于开发集分析。不得仅为增加组内方差而随意修改聚合规则。

“最看重A，其次B”若表达了跨字段的严格优先级，第一版不假装最小值函数能完整表达该语义。这类任务需要单独审核并扩展注册规则，之后才能纳入主训练集。

### 4.9 只有方向、没有数值锚点

“越轻越好”“容量大一些”没有明确目标或界限时，不能直接构造线性函数。

第一版要求任务构建阶段取得可公开的数值锚点，否则暂不纳入该类任务。不得使用本轮 Agent 找到的候选最小值、最大值进行动态归一化，避免少看商品反而得到高分。

### 4.10 偏好信息缺失

在全部必须条件可验证且通过的前提下：

- 某个软偏好的事实未知：该项 s=0，status=unknown。
- 事实在后台可知，但 Agent 实际收到的信息没有支持该偏好：该项按已核验满意度0计算，记录 evidence_missing。
- 两种情况都不能获得“所有偏好已满足”的标签。
- 仅因一个可妥协偏好未知，不把整个样本标为 reward_valid=false。

这一分数表示“未取得可验证的偏好满足”，并不声称商品一定不满足。

如果未知的是允许范围或必须条件，例如无法判断颜色是否属于{白色, 黑色}，则执行必须条件的未知规则，不能按普通软偏好缺失处理。

## 5. 价格效用

只有用户明确提出省钱目标，且具有可靠参考预算 B>0时启用：

$$
S_{\mathrm{price}}=
\operatorname{clip}\left(\frac{B-p}{B},0,1\right)
$$

其中 p 为最终合法规格的价格。

- 未提出省钱目标：S_price=1，作为同任务内的常数。
- 明确提出省钱目标但无可用参考值：先解决合同可评分性，不能静默当作未提出目标。
- 超预算：先判定错误购买，不进入价格效用加分分支。
- 未声明预算：不从 Gold 商品价格推导预算。
- 运费、优惠券、会员价和数量折扣，只有环境能可靠核验时才能进入实际支付价格。

例：“预算5000元，尽量便宜”：

- 4500元：S_price=0.10。
- 4000元：S_price=0.20。

此函数奖励预算内的节省，不声称商品是全库最低价。“必须买全库最低价”是另一个需要穷举或固定全库参考证明的任务类型，不属于本函数的保证范围。

## 6. 商品事实与 Agent 证据

维护两个独立层次：


| 层次          | 来源                                      | 用途                   |
| ------------- | ----------------------------------------- | ---------------------- |
| 订单事实      | 环境商品记录、最终SKU、价格解析、购买回执 | 确定实际买了什么       |
| Agent已获证据 | 购买前实际发送给Agent的工具观察           | 确定购买决策是否有依据 |

关键事实包括请求类目、所有必须条件、最终合法规格和最终价格。必须核验最终价格，即使用户没有预算上限，也不能在价格不确定时判定可靠完成购买。

证据要求：

1. 记录字段、ASIN、规格状态、步骤和原始观察位置。
2. 必须来自 Agent 实际收到的文本或结构化观察。
3. 后台存在但未展示的字段、渲染时被截断的字段，不算 Agent 证据。
4. 更换影响价格的规格后，旧价格证据失效。
5. 商品静态属性可以保留，不因普通翻页机械失效。
6. 购买后回执可证明订单事实，但不能追溯补齐购买前缺失的证据。
7. 缺省规格若被环境清楚展示且合法，可视作最终规格；不强制每个轴都额外点击一次。
8. 同一事实冲突时，按冻结的来源优先级处理；仍不能解决则记 unknown。

关键证据覆盖率：

$$
C_{\mathrm{evidence}}=
\frac{\#\text{已核验关键事实}}{\#\text{关键事实总数}}
$$

购买正奖励要求覆盖率为1。查看页面次数、搜索次数或自由文本中的自我声明，均不能替代事实覆盖。

## 7. 错误购买如何判分

### 7.1 确定性判定流程

1. 环境读取冻结合同。
2. 从最终订单读取真实字段。
3. 执行每个必须条件的比较器。
4. 生成 pass / fail / unknown 和证据来源。
5. 对每个已证实的 fail，查找合同中已冻结的严重度规则。
6. 汇总最严重违反项，计算错误奖励。

Agent 不选择严重度、不填写扣分理由、不决定 reward_valid，也不能通过解释“我觉得可以接受”改变评分。

### 7.2 默认严重度表

对每个已证实违反项 i，确定 d_i：


| 错误类型                       | 默认d_i | 不含操作成本的错误奖励 |
| ------------------------------ | ------: | ---------------------: |
| 明确颜色、非核心外观错误       |    0.30 |                  -0.72 |
| 明确品牌错误                   |    0.60 |                  -0.84 |
| 型号、容量、尺码等明确规格错误 |    0.80 |                  -0.92 |
| 已证实缺少用户要求的核心功能   |    0.90 |                  -0.96 |
| 品类错误、明确无法实现请求用途 |    1.00 |                  -1.00 |

该表是损失严重度的工程排序，不是退货费用或用户容忍概率。

使用原则：

- “不要红色”按颜色错误处理，不因为有否定词就自动变成最严重错误。
- 材质影响用途或安全兼容性时，应按明确用途规则归类，不能一律按外观处理。
- 用户明确用途改变某项的重要性时，可以在审核阶段配置严重度覆盖；必须记录依据和规则ID。
- 单凭“必须”二字不能推导任意数值；它首先确定该条件不可违反。
- 运行期间不接受任何严重度覆盖。
- 多个规则命中同一语义错误时只保留一个规范化违反项。
- 无法可靠确定严重度规则的任务先审核，不让 Agent 补分。

合同不再使用含糊的 critical / major 标签代替数值；直接存储 rule_id 和 severity_value。

### 7.3 超预算严重度

仅在 p>B 且 B>0 时使用：

$$
d_{\mathrm{budget}}
=
0.25+0.75
\min\left(1,\frac{p-B}{0.20B}\right)
$$


| 超预算比例 | 严重度 | 不含操作成本的奖励 |
| ---------: | -----: | -----------------: |
|         1% | 0.2875 |             -0.715 |
|        10% |  0.625 |             -0.850 |
|  20%及以上 | 1.0000 |             -1.000 |

价格比较使用规范化货币精度，例如人民币分，不用浮点误差制造超预算。恰好等于“以内”的上限通过。

任何实际超预算均为错误购买。连续函数只表达错误程度，不表示允许小幅超预算。

### 7.4 总错误奖励

设已证实违反集合为 V：

$$
D=\max_{i\in V}d_i
$$

$$
R_{\mathrm{wrong}}
=
\operatorname{clip}(-0.60-0.40D-C_{\mathrm{waste}},-1,1)
$$

例如，颜色错且容量错：D=max(0.30,0.80)=0.80，奖励为-0.92减操作成本。

采用最大值防止同一个问题被拆成多条要求后重复放大。其限制是：在最严重错误相同的情况下，多一个轻微错误可能不改变标量奖励；全部违反项仍保留在审计字段中。

### 7.5 已知错误与未知事实的优先级

- 可信证据已确认必须条件违反：判 wrong_purchase。
- 另一项未知不能抹去已知错误。
- 若未知项可能包含更严重错误，按已知违反项计算，标记 violation_assessment_complete=false；它是有效的确定性错误分，不声称已知道全部损失。
- 无已知违反，但必须事实或最终价格无法由环境确定：reward_unverifiable。
- 环境事实完全符合，但 Agent 没有取得关键证据：unverified_purchase。

任务合同本身无效或购买记录损坏时，不使用上述“已知错误优先”规则强行评分，应记录无效原因。

## 8. 完整终局奖励与类型

### 8.1 合格购买效用

满足购买正奖励条件后：

$$
R_{\mathrm{purchase}}
=
\operatorname{clip}
\left(
0.80+
0.10S_{\mathrm{pref}}+
0.05S_{\mathrm{price}}+
0.05I_{\mathrm{gold}}
-C_{\mathrm{waste}},
-1,1
\right)
$$

各项含义：

- 0.80：完成用户授权的可靠购买。
- 0.10×S_pref：非价格偏好满意度。
- 0.05×S_price：明确省钱目标的效用；没有目标时为固定0.05。
- 0.05×I_gold：严格 Gold 对齐奖励。
- C_waste：有限的操作浪费成本。

I_gold=1必须满足完整 gold_purchase 条件，不能仅凭 ASIN 相同获得。

### 8.2 购买类型的互斥定义

按以下顺序判定：


| 顺序 | reward_type                    | 判定                                                                     |
| ---: | ------------------------------ | ------------------------------------------------------------------------ |
|    1 | reward_unverifiable            | 合同无效或关键订单记录损坏，无法建立可信评分依据                         |
|    2 | wrong_purchase                 | 有可信、已证实的必须条件违反                                             |
|    3 | reward_unverifiable            | 无已知违反，但必须事实、合法SKU或价格无法确定                            |
|    4 | unverified_purchase            | 订单事实符合，但购买前关键证据不完整                                     |
|    5 | acceptable_compromise_purchase | 必须条件通过且证据完整，但至少一个非价格偏好未达首选，或偏好证据未知     |
|    6 | gold_purchase                  | 全部必须条件和关键证据通过，所有非价格偏好已证实达到首选，且目标ASIN匹配 |
|    7 | valid_alternative_purchase     | 与Gold相同的满足条件，但目标ASIN不同                                     |

没有非价格偏好时，“所有非价格偏好达到首选”按真处理。连续偏好达到满意度1即达到该偏好的首选区间。

省钱目标影响价格效用，不要求达到理论价格0才能判为Gold。Gold也不代表全库最低价。

未在用户指令中声明的 Gold 规格不添加隐藏要求。最终SKU必须合法，并满足用户已声明的规格条件。

### 8.3 核心布尔字段

- reward_valid：该规则结果是否可用于训练与统计；失败不等于无效。
- purchase_success：只对 gold_purchase 和 valid_alternative_purchase 为true，表示全部已评分需求与首选偏好满足。
- acceptable_purchase：对 Gold、完整替代和授权妥协三类为true。
- strict_success：仅完整、合法、有效的 gold_purchase 为true。
- sampling_invalid：对奖励无效或独立的基础设施无效事件为true。

保留 purchase_success 与 acceptable_purchase 两个字段，可分别报告完整满足和用户允许的妥协。

### 8.4 未核验与不可评分


| 情况                |            分数 | reward_valid |
| ------------------- | --------------: | ------------ |
| unverified_purchase |   -0.60-C_waste | true         |
| reward_unverifiable | 0，仅作数值占位 | false        |

不可评分的0不参与组内相对奖励计算，也不表示中性购物结果。

## 9. 操作成本

$$
C_{\mathrm{waste}}
=
\min(0.05,\ 0.01N_{\mathrm{redundant}}+0.01N_{\mathrm{invalid}})
$$

- N_redundant：相同有效状态下重复执行相同操作，既不改变有用状态，也没有增加有效信息。
- N_invalid：Agent造成的非法工具名、参数、不可访问商品ID或不合法状态动作。
- 同一次事件最多计一次成本。
- 网络错误后的必要重试、返回已查看商品完成购买、修正规格不直接判为浪费。
- 普通搜索、详情核验和必要规格选择不按步骤扣分。
- 以语义等价参数和规范化状态识别重复，不能靠空格或大小写刷新计数。

该成本统一在终局扣除。训练适配器不再叠加另一个长度成本；最终环境奖励与训练所用 terminal_utility 保持一致。

35步作为资源上限保留。循环检测需要状态、动作和证据联合判断；建议初值为同一状态动作连续重复3次，或连续4次既无有效状态变化也无新证据。购买和合法停止一旦成功提交，应先处理终局，再检查步数截断。

## 10. 停止与资源耗尽

### 10.1 可接受候选

可接受候选必须有一套合法、可执行的规格组合，且已获证据证明：

- 所有必须条件通过。
- 最终组合价格通过预算条件。
- 规格、价格与同一候选一致。
- 用户明确允许该组合。

可妥协偏好不达首选，不阻止其成为可接受候选。核验依据来自 Agent 已见信息；后台知道有Gold存在，不能直接算成 Agent 已发现可购买候选。

### 10.2 有限的停止质量

对相关且已打开的候选 c，定义：

$$
q_c=
\frac{\#\text{候选c已核验的关键事实}}
{\#\text{该任务固定的关键事实义务}}
$$

$$
Q=\max_c q_c
$$

无相关候选时 Q=0。候选必须匹配请求品类，且来自与任务相关的可见搜索或浏览；无关商品不贡献Q。

关键事实义务在任务开始时固定并去重，包含必须条件、合法规格和最终价格。pass和fail都可以算已核验，unknown不能算。同一候选的覆盖度只计算一次，不能把多件商品的不同字段拼成一件虚构订单。

Q只衡量相关候选的调查完整程度，不证明整个商品库没有合格商品。
规格、合法 SKU 和最终价格必须来自同一 ASIN 的同一规格指纹；静态商品字段可以跨规格复用，不能把不同变体的证据拼成一个候选。

### 10.3 停止奖励

下表先算基础值，再统一减C_waste并裁剪到[-1,1]：


| 条件                         | reward_type                    |    基础奖励 |
| ---------------------------- | ------------------------------ | ----------: |
| 已知存在可接受候选却主动停止 | stop_with_acceptable_candidate |       -0.40 |
| 无已知可接受候选，且Q>0      | graceful_stop                  | -0.30+0.20Q |
| 无已知可接受候选，且Q=0      | early_abstain                  |       -0.30 |
| 达到35步上限                 | max_steps                      |       -0.40 |
| 确认陷入重复循环             | repeat_loop                    |       -0.50 |

graceful_stop最高基础奖励为-0.10，表示有依据地避免错误购买，但购买任务尚未完成。第一版任务要求存在可达正确购买，因此停止不计为成功。

该设计仍可能让只调查一个不合适候选的轨迹获得较轻负分。必须在开发集监控放弃率；不能把这一分数解释为完整搜索的证明。

Agent直接结束生成但没有调用合法停止动作，不生成graceful_stop；训练适配器应记录策略未完成终局的原因，并给有效策略失败分（建议-0.40）。网络、服务中断和日志损坏另标基础设施无效，不冒充策略停止。

## 13. 数据构建、SFT、GRPO与评估

### 13.1 任务准入

进入主数据集前：

1. 合同已审核，所有显式要求均被覆盖或明确解释。
2. 必须条件无矛盾，比较器和偏好函数受支持。
3. Gold可通过公开工具和合法动作到达。
4. Gold规格、价格和必要证据可解析，非价格偏好能达到首选。
5. 条件替代、数量或服务类要求未超出环境能力。
6. 训练、开发、评估按task_id和规范化需求去重，并检查重复或近重复任务泄漏。

用于参数调整的开发集独立于训练集和最终评估集。核查评估任务的合同可评分性，不等于用其结果调参数。

### 13.2 SFT

SFT默认只接受：

- 完整合法购买终局。
- reward_type=gold_purchase。
- reward_valid=true。
- 关键证据完整，工具调用合法。
- 与评估集无重叠。
- 无基础设施错误或无法还原的订单状态。

奖励用于采集筛选和审计，SFT并不直接优化这个标量公式。

可以复用满足要求的原始任务、采集工具和轨迹结构；已有轨迹需要按冻结合同重新验证。缺失关键观察、最终规格或价格时，不能靠补写奖励值变成合格样本。非Gold正分轨迹不自动进入主SFT集。

### 13.3 GRPO

- 将完整终局效用作为序列级奖励。
- 保留wrong_purchase、unverified_purchase和有效停止等策略失败样本。
- 环境不可评分和基础设施无效样本设sampling_invalid=true。
- 按完整prompt组处理采样无效；不能把无效0作为普通负样本，也不能随意删掉单个成员后沿用未检查的组归一化。
- 记录无效组比例、同分组比例、奖励类型分布和停止比例。

第一版仍是序列级监督。增加奖励分项不会自动实现逐步信用分配。

负奖励也可能在全失败组中得到正的相对优势。因此“错误购买总是负数”不等于模型永远不会增强某种失败行为。需要结合成功率、错误率、组内分布和停止率判断训练效果，不能只关注平均奖励。

### 13.4 评估指标

所有率均以完整指定任务集为分母；无效或未完成任务不从成功率分母删除。


| 指标             | 定义                                                   |
| ---------------- | ------------------------------------------------------ |
| 严格Gold成功率   | 完整合法且有效的gold_purchase比例                      |
| 完整需求满足率   | 有效Gold与完整替代购买合计比例                         |
| 可接受购买率     | 完整购买与授权妥协合计比例                             |
| 授权妥协率       | acceptable_compromise_purchase比例，另报告偏好未知子集 |
| 错误购买率       | wrong_purchase比例及各违反字段分布                     |
| 未核验购买率     | unverified_purchase比例                                |
| 停止率           | 各停止类型分别报告                                     |
| Reward有效率     | reward_valid=true的任务比例                            |
| 固定分母平均奖励 | 全任务记录分数之和除以任务总数，无效0需明确是占位      |
| 有效样本平均效用 | 仅有效终局的均值，同时展示有效率                       |
| 平均操作成本     | 明确冗余和非法动作的成本统计                           |

Reward无效比例明显变化时，不能只比较有效样本平均效用，避免由样本选择造成误判。

## 14. 实施范围与验证

### 14.1 需要实现的模块

- 合同编译器与冻结元数据。
- 确定性条件比较器和偏好函数注册表。
- 最终SKU与价格解析。
- Actor实际观察对应的证据账本。
- 错误严重度规则表。
- 终局分类和RewardResult。
- SFT准入、GRPO适配和评估统计。

使用仓库现有数据构建、规格解析、工具调用和训练流程作为实现基础。奖励版本、环境清单、校验器、数据元数据和测试应整体同步，保持单一生效契约，不增加历史版本兼容启动器。

### 14.2 必须通过的规则验证

- 相同输入重复评分完全一致。
- 同义指令经过审核后得到相同合同。
- 必须条件失败不能被偏好、低价或ASIN命中抵消。
- 集合允许、偏好排序和条件替代不混淆。
- 单位换算、预算边界、型号边界和否定范围正确。
- 偏好函数在允许范围内单调且有界。
- 没有偏好时S_pref=1；解析不了偏好时不能套用该规则。
- 未知软偏好取保守分并记录unknown，不伪造成fail。
- 已知硬错误不因另一字段未知被抹去。
- Gold ASIN错误规格不能成为gold_purchase。
- 规格变化会使相关价格证据失效。
- 购买回执不能反向补全决策前证据。
- 价格目标只计一次。
- 重复动作不增加偏好、调查质量或证据覆盖。
- 终局类型互斥，所有分项与总分一致。
- 错误购买、无证据购买与基础设施无效不会混为一类。
- 评分私有字段不进入Actor提示或SFT训练消息。

### 14.3 开发集人工核验

构造独立开发案例，覆盖每种偏好类型、边界、错误严重度和未知状态。审核者只根据用户要求、订单事实和规则检查：

- 合同是否忠实表达需求。
- 正负分支是否正确。
- 偏好排序是否合理。
- 错误严重度是否稳定。
- 是否出现容易获利的提前停止或信息缺失行为。

所有参数调优在开发集完成。文档审批本身不授权启动训练、模型合并或200题评测。
